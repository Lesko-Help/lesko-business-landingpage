# wallets
Status: draft
Kind: helper
Summary: PayPal, Apple Pay and Google Pay on `/checkout`: one shared wallet seam plus one small file per method, every method off by default
Part of: `docs/specs/INDEX.md` · Deploy: push to `main` (Cloudflare Workers Builds) · Updated: 2026-10-09
Reads: the Recurly public key `checkout.html` already fetched from `/api/config`; Recurly.js v4's `recurly.ApplePay()` and `recurly.GooglePay()`; and, for PayPal only, PayPal's own JS SDK with our PayPal client id (see P3).
Writes: for Apple Pay and Google Pay, `POST /api/subscribe` with a wallet token in place of a card token. **PayPal writes nothing to our Worker**: it creates the subscription inside PayPal and then sends the buyer to `/welcome` (P5).

## Overview

*What it is for:* let a buyer on `/checkout` pay with PayPal, Apple Pay or Google Pay instead of typing a card, on the same page and the same purchase call.
*What it owns:* `assets/wallet-common.js`, `assets/wallet-paypal.js`, `assets/wallet-apple-pay.js`, `assets/wallet-google-pay.js`, the `#wallets` row in `checkout.html`, and the file `/.well-known/apple-developer-merchantid-domain-association`.
*What it depends on:* for Apple Pay and Google Pay, Recurly.js v4, the `worker` module's wallet branch in `/api/subscribe` (W1), and a Recurly gateway that supports the method — **none is in place**, see Decisions. For PayPal, none of that: a PayPal REST client id, two PayPal billing plans Lesko already owns, and lesko-provisioning's PayPal rail, which is live (Decisions, 2026-10-17).
*Public entry points:* `window.LeskoCheckout` (published by `checkout.html`), `window.LeskoWallets.payWithWallet(method, token, buyer)` and `isOn(method)`, and one `init()` per method file.
*Not in scope:* the card form, the address rules and the page's look (`page`); the Recurly purchase itself (`worker`); provisioning and email (lesko-provisioning); every gateway, Apple Developer and Google Pay console setting, none of which a Claude session can reach.
*Secrets:* none of its own. The Recurly public key comes from `/api/config`; the Google merchant id, the Apple merchant id and the PayPal **client id** are public identifiers and are typed in the clear. The PayPal client *secret* is never needed here and must never appear in the repo — the subscription is created by the browser against a plan, not by a server call.
*Personal data:* each wallet hands back the buyer's email and, when the sheet is asked for it, first and last name. They travel to Recurly exactly as the typed ones do (`worker` B1) and are never logged.

Used by: `checkout.html`.

## Functions

### LeskoCheckout — the seam `checkout.html` publishes

*Signature:* `window.LeskoCheckout = { plan(), total(), showError(message), busy(on, label), finish(result, tokenId, buyerEmail), walletsRow(), onReady(callback) }` — set by `checkout.html`'s inline script once the plan is known, before any wallet file runs.

*What it does:*
- K1: `plan()` returns the active plan key (`monthly`, `half-year` or `yearly`, the same fallback the card path uses) and `total()` its displayed total as a plain number of USD, e.g. `29.95` — a wallet sheet needs the amount, not the `$29.95` string.
- K2: `showError(message)` is the one the card path already uses: it fills the red `#payMsg` box and scrolls to it. A wallet never writes to the DOM itself.
- K8: `busy(on, label)` is the card path's own lock, lent out (2026-10-23). `busy(true, label)` disables the `#payBtn` submit button and replaces its text with `label`; `busy(false)` re-enables it and restores `Pay <total> now`. A wallet file calls it with `true` and never with `false`. Why it is on the seam at all: a wallet can take the buyer's money before this page knows anything about it, and only this page can disable its own button — so the lock has to be lendable. Why a wallet never unlocks: see P10. A wallet must tolerate its absence (`typeof` check), because it joined the seam after `wallet-paypal.js` shipped and a cached page may not have it.
- K3: `finish(result, tokenId, buyerEmail)` is the one the card path already uses, with one argument added for wallets. On `ok` it saves `{email, company, plan, t}` in `localStorage` and goes to `/welcome?email=…&plan=…`; on `three_d_secure_action_token_id` it opens `recurly.Risk().ThreeDSecure()` and re-submits with `subscribe(tokenId, …)`; otherwise it calls `showError`. A wallet reuses it, so there is exactly one success path and one 3-D Secure path on the page.
  - K3a: `tokenId` is **not** optional. The 3-D Secure branch re-submits the *original* payment token beside the bank's result token, so a caller that omits it posts `undefined` the one time the bank was willing to approve. A wallet passes the token id it just handed to `payWithWallet`.
  - K3c (open gap, recorded 2026-10-12, overseer review of `wallet-paypal`): the 3-D Secure branch is **card-only**, even though every wallet goes through it. It re-enters `checkout.html`'s own `subscribe()`, which builds a card-shaped body — no `wallet` field, and the name and email read back off `#email`/`#first_name`/`#last_name`. So a wallet buyer who never typed a name would be answered by the Worker's 400 "Please enter your first and last name." at the one moment the bank was willing to approve, on a token that is single use. Doubly unreachable today: no wallet switch is on, and the hand-back cannot fire at all (worker.md, 2026-10-09 open defect — S4 reads `err.three_d_secure_action_token_id` where Recurly v3 nests it under `error.transaction_error`). Both belong to the 3DS task, not to a wallet branch: whoever fixes the hand-back must fix the retry in the same worktree, or fixing one turns a silent dead branch into a live broken one. A wallet branch only carries a comment at the seam saying so.
  - K3b: `buyerEmail` exists because `finish` otherwise reads the email from the **card form's own input** (`var email = document.getElementById('email')`). A wallet buyer never types there, so without this argument a wallet purchase reaches `/welcome?email=&plan=…` with the address empty — and `/welcome` fires the GA4 `purchase` event while lesko-provisioning keys on that address. `checkout.html` reads `(buyerEmail || email.value).trim().toLowerCase()` — the normalising applies to **both** sources, and `payWithWallet` normalises the same way once before it posts, so the address in Recurly's account code, in `localStorage` and in the `/welcome` link is always the same string. Why it is spelled out: the card path has always trimmed and lower-cased (in `subscribe()` and in `finish()`), and a wallet that reports `Buyer@Example.COM` would otherwise open a second Recurly account for a buyer who already has `buyer@example.com` — and lesko-provisioning keys on that address. The card path passes no third argument, so it behaves exactly as before.
- K4: `walletsRow()` returns the `#wallets` element, or `null` when the markup is missing — a wallet file that cannot find its row does nothing rather than throwing.
- K6: `onReady(callback)` runs `callback` once `recurly.configure()` has succeeded, immediately if it already has. A wallet file that calls Recurly mounts **only** from inside it — which since 2026-10-17 means Apple Pay and Google Pay, not PayPal: PayPal goes straight into PayPal (P5) and never touches `recurly`, so it mounts on `DOMContentLoaded` and waiting for a Recurly it does not use would only let a failed `/api/config` hide its button. It is still safe on this page because `checkout.html`'s inline seam script is not deferred, so `window.LeskoCheckout` exists before any `defer` wallet file runs, let alone before `DOMContentLoaded`. Why it is not optional: `checkout.html` configures Recurly only after its async `fetch('/api/config')` answers, which is later than `DOMContentLoaded`; a wallet file that mounts on `DOMContentLoaded` calls `recurly.GooglePay()` (or `PayPal()`, or `ApplePay()`) against an unconfigured `recurly`, which throws — and every wallet file catches that throw by design, so the button silently never appears and no error is logged anywhere.
  Two ordering rules make K6 safe, both found the hard way in `wallet-paypal`'s review (2026-10-12), where breaking them killed the card checkout silently the moment a wallet switch was flipped:
  - `checkout.html` marks itself ready **last** — after `recurly.Elements()` and after `card.attach('#recurly-card')`, not between `recurly.configure()` and them. The callbacks run synchronously inside that function, so anything they do happens before whatever follows the call.
  - the seam wraps **each** callback in its own `try`/`catch`. A wallet file that throws must not stop the card field attaching, must not stop the next wallet file, and must not reach `checkout.html`'s `fetch('/api/config')` chain, whose `.catch` is empty and would swallow it without a trace. A wallet file still catches its own throws as well (P4/G4/A4); this is the backstop for the one it misses.
- K7: **PayPal reuses `finish()` unchanged** (2026-10-17). It calls `finish({ok: true}, subscriptionID, buyerEmail)`: the `ok` branch saves `localStorage` and goes to `/welcome`, which is exactly right, and the 3-D Secure branch cannot fire because PayPal's result carries no `three_d_secure_action_token_id` — so K3c's card-shaped retry is not a risk on this route. Why reuse rather than add a `finishPayPal`: the page gets one success path and one `/welcome` link, and the K3b email normalising applies to PayPal for free. The `tokenId` argument holds a PayPal subscription id here and is never re-submitted; it reaches only `localStorage`.
- K5: publishing this seam changes no card behaviour. `checkout.html` keeps its no-op `window.LeskoAnalytics` stand-in and its existing submit handler; the inline functions are assigned to `window.LeskoCheckout` instead of being renamed or moved.

*Examples:* on `/checkout?plan=yearly` -> `plan() === 'yearly'`, `total() === 149.95`. With the card form's email box holding `a@b.co`, `finish({ok:true}, 'tok-1')` -> `location.href === '/welcome?email=a%40b.co&plan=yearly'`. With that box empty, as it is for every wallet buyer, `finish({ok:true}, 'tok-1', 'w@b.co')` -> `/welcome?email=w%40b.co&plan=yearly`, and `finish({ok:true}, 'tok-1')` -> `/welcome?email=&plan=yearly`, which is the bug K3b exists to stop.

*Inputs:* the page URL and the `PLANS` table already in `checkout.html`. *Outputs:* the seven functions above on `window`.

*Errors:* none surfaced; a missing `#wallets` row is K4's `null`.

*Test:* `scripts/test-wallet-seam.sh .` — jsdom loads the real `checkout.html` with Recurly.js stubbed, and checks K1–K8: the seven functions exist, `plan()`/`total()` for all three plans and for a junk `?plan=`, `showError` fills `#payMsg`, `finish({ok:true,…})` sets the `/welcome` URL and the `localStorage` key, the card submit path still reaches the token call, **`finish({ok:true},'tok-1','w@b.co')` with the card email box empty puts `w%40b.co` in the `/welcome` URL and in `localStorage`** (K3b), **the 3-D Secure branch re-submits with the `tokenId` it was given, not `undefined`** (K3a), and **`onReady` fires only after `recurly.configure()`, fires immediately when called afterwards, and — with a wallet switch on and a wallet SDK constructor stubbed to throw — the card field is still attached and the throw never escapes** (K6). That last check is the one the first review of `wallet-paypal` missed: proving a callback fires says nothing about what fires after it. Red first against `origin/main` (`window.LeskoCheckout` is undefined there). `busy` (K8) is pinned by `test-wallet-paypal.sh` instead, where the wallet that uses it lives: that suite drives `onApprove` and asserts `#payBtn` is disabled while the address lookup is still in flight (P10).

### payWithWallet(method, token, buyer) / isOn(method) — `assets/wallet-common.js`

*Signature:* `window.LeskoWallets = { payWithWallet(method, token, buyer), isOn(method), WALLETS }`. `method` is one of `paypal`, `apple_pay`, `google_pay` — but since 2026-10-17 **`payWithWallet` is Apple Pay's and Google Pay's only**: PayPal goes straight into PayPal and never posts to our Worker (P5), so it uses `isOn('paypal')` and nothing else here. `paypal` stays an accepted value because `worker` W1 still accepts it and removing it would be a second change for no gain. `token` is the Recurly token id the wallet produced; `buyer` is `{email, first_name, last_name}` as the wallet reported it, any of them possibly empty.

*What it does:*
- C1: `WALLETS = { paypal: true, apple_pay: false, google_pay: false }` sits at the top of the file and is the only switch. `isOn(method)` returns its flag; a method whose flag is `false` mounts no button, loads no wallet SDK and makes no network call, exactly as `GA4_MEASUREMENT_ID = ''` switches analytics off. **`paypal` ships `true` since 2026-10-17** (`11093ba`), once its three plans existed in Lesko's own PayPal account at the page's own prices. **`apple_pay` and `google_pay` still ship `false`** until Martin's gateway work is done and one real purchase has gone through on that method.
- C2: `payWithWallet` POSTs the same JSON body the card path posts — `{plan, token, email, first_name, last_name, company}` — plus `wallet: method`, to `/api/subscribe`, and hands the parsed answer straight to `LeskoCheckout.finish(result, token, buyer.email)` — both extra arguments always, per K3a and K3b. There is no second route and no second success path.
- C3: the buyer's details are resolved **wallet first, then the page's own fields**: `(buyer.email || document.getElementById('email').value)`, the same for `first_name` and `last_name`, each trimmed (and the email lower-cased) exactly as K3b pins it; `company` has no wallet source at all and is read straight off `#company`. Only when the result is still empty is the purchase refused before the POST, with `showError("We did not get an email address back from <wallet>. Please pay by card instead.")` — Recurly's account code is the email (`worker` B1), so a purchase without one cannot be built. Why the fallback, amended 2026-10-09: on this one-step page `#email`, `#first_name` and `#last_name` are `required` fields in panel 1 ("Your details") and the wallet button sits in the summary panel below them, so by the time a buyer clicks it they have almost always typed their address already. Whether Recurly's own `token` event carries an email is **unverified for all three methods** — there is no wallet-capable gateway on this site to test against (see Decisions) — so a wallet-only read would refuse every purchase on the day a gateway is switched on, with the address sitting in the form unread. The wallet's own address still wins when it gives one, because that is the account the buyer actually paid from. The refusal stays reachable: the wallet button is `type="button"`, so it bypasses the form's HTML validation and a buyer can click it with every field empty — which is also why `worker` W1 keeps the names optional.
- C4: before the POST it sends GA4 `add_payment_info` through `window.LeskoAnalytics.track()` with the plan, the USD price and `payment_type` set to `PayPal`, `Apple Pay` or `Google Pay`, so a wallet purchase is told apart from a card one in GA4. For that to work the **card** path must name itself too: `checkout.html`'s own `add_payment_info` sends `payment_type: 'Credit Card'`. Until `wallet-paypal` it sent no `payment_type` at all, and GA4 invents no default for a missing parameter (amended 2026-10-12, overseer review of `wallet-paypal`, which had asserted the opposite in a code comment) — so without this every card purchase would land in GA4 with the field blank and only wallet purchases would be labelled, which is not a comparison.
- C5: a network failure or a non-JSON answer calls `showError` with the card path's generic sentence ("The payment did not go through…"); nothing is retried, because a wallet token is single use.
- C6: the file is inert when loaded on a page that has no `window.LeskoCheckout` — it defines its functions and does nothing else, so `index.html` or `welcome.html` could load it harmlessly.
- C7: every wallet reports its button funnel with the same four GA4 events, sent through `window.LeskoAnalytics.track()`, and no wallet invents other names. `wallet_click`: the buyer pressed the wallet's button, counted before anything else, so it is the whole denominator. `wallet_click_refused`: that same click was refused before the wallet's own window opened; it is sent in addition to `wallet_click`, never instead of it, and names why in `reason`. **PayPal has not sent it since 2026-10-23** — it no longer refuses a click at all (P6), so of these four it sends three. The name stays in C7 because Apple Pay and Google Pay still refuse an empty address in `payWithWallet` (C3), and because a funnel report that loses a series is easier to read than one that loses a name. Anyone charting refusals should know the PayPal series ends on that date. `wallet_cancel`: the buyer closed the wallet's window. `wallet_error`: the wallet reported a real failure; our own missing-email refusal is not one. Every event carries exactly the C4 shape of `add_payment_info`: `currency: 'USD'`, `value` (the plan's USD price as a number), `payment_type` (`PayPal`, `Apple Pay` or `Google Pay`, the same label as C4) and `items: [{ item_id, item_name, price, quantity: 1 }]`. Never sent: the wallet's error text, the buyer's email or any other personal data. A failing `track()` is swallowed, because analytics must never stop a payment. `apple_pay` and `google_pay` must send these same names and this same shape when they are switched on.
- P10: **`onApprove` locks the card form before anything else** (2026-10-23). Its first statement is `LeskoCheckout.busy(true, 'Finishing your order…')` (K8), before any branch, and nothing ever unlocks it. Why: PayPal creates its subscription inside PayPal and only then hands control back, and `finish()` — which is what used to disable the button — now runs after an address lookup (P6). In between, a buyer who had already paid saw a live `Pay $29.95 now` and could be charged a **second** time on the Recurly rail. The failure branches lock too, the one where PayPal hands back no subscription id included: there the money may well be gone, so a dead button beside the "contact support" message is right and a live one is not. The label is deliberately not "Payment received" — on that branch we do not know that it was; `finish()` sets that wording itself on the success path. A seam without `busy` must degrade, not throw (K8). Test it **while the lookup is still in flight**: a check after it passes with no lock in the code at all, because `finish()` locks on its way out — and the mutant that proves such a check is moving the lock later, not deleting it.

*Examples:* `payWithWallet('paypal', 'tok-1', {email:'a@b.co'})` on `?plan=monthly` -> `POST /api/subscribe {"plan":"monthly","token":"tok-1","email":"a@b.co","wallet":"paypal",…}` -> `finish()` -> `/welcome?email=a%40b.co&plan=monthly`. The same call with `{email:''}` -> no POST at all, and the `#payMsg` box names PayPal.

*Inputs:* `WALLETS`, the three arguments, `window.LeskoCheckout`, `window.LeskoAnalytics`. *Outputs:* one `fetch` to `/api/subscribe`, one GA4 event, and whatever `finish()` does.

*Errors:* every failure is shown in `#payMsg`; nothing is alerted from the browser. A decline is alerted server-side by `worker` S5, which now also records which wallet it was (W2).

*Test:* `node scripts/test-wallet-common.js assets/wallet-common.js` — loads the file in a `vm` with a stubbed `fetch`, `LeskoCheckout` and `LeskoAnalytics`: C1 (`paypal` is `true` and the other two are `false` **in the file as shipped**, and `isOn` reports them), C2 (the exact POST body, including `wallet`), C3 (no POST and the named error on an empty email), C4 (one `add_payment_info` with the right `payment_type`), C5 (a rejected `fetch` shows the generic sentence and posts once), C6 (no throw without `LeskoCheckout`). Red first against `origin/main` (the file does not exist there).

### init() — `assets/wallet-paypal.js`

*Signature:* `assets/wallet-paypal.js`, loaded by `checkout.html` with `defer`; it runs its own `init()` on `DOMContentLoaded`.

*Route:* **straight into PayPal**, the same rail the ClickFunnels order pages have used for years — not through Recurly. Input: a buyer on `/checkout?plan=…` who clicks the PayPal button. Output: a live subscription inside PayPal, the buyer on `/welcome`, and MN access granted by lesko-provisioning off PayPal's own webhook. Recurly is not involved and sees nothing.

*What it does:*
- P1: returns at once unless `LeskoWallets.isOn('paypal')`, `LeskoCheckout.walletsRow()` and a plan id for this `?plan=` are all present — no PayPal SDK is fetched when the switch is off, and no button appears on a plan the map has no entry for.
- P2: the plan map, a constant at the top of the file. Since 2026-10-17 the three ids are **ACTIVE plans in Lesko's OWN PayPal merchant account** (product `PROD-25B93089XF9559540`), not copied from ClickFunnels: `monthly` → `P-7R176589BE0160805NLJVCFI` ($29.95/month), `half-year` → `P-2GV64945HR320740CNLIP2HY` ($89.95/6 months), `yearly` → `P-8M862053KT491162FNLJVCFI` ($149.95/year). All three match what `checkout.html` displays and what the card rail charges, so the price gap recorded on 2026-10-17 is closed. The ids that shipped before were another merchant's and answered HTTP 404 for our credentials — **never wire `P-7TV41146KY851263NROQAXEQ` or `P-80J45642K6983362LS2OVYFQ` again**. A plan the page offers but the map lacks still shows no PayPal button (the `!planId` guard in P1).
- P3: loads PayPal's current JS SDK once, `https://www.paypal.com/sdk/js?client-id=<PAYPAL_CLIENT_ID>&vault=true&intent=subscription&currency=USD&components=buttons&disable-funding=card` — the last parameter is P8's funding rule, which PayPal's SDK takes only in this URL and nowhere in `Buttons({…})`, and renders one `paypal.Buttons({…})` into `#wallets`. `PAYPAL_CLIENT_ID` is a constant at the top. Since 2026-10-17 it ships the **real 80-character client id** of Lesko's own PayPal account, read from the `paypal-client-id` secret in GCP project `lesko-486515`. It is PayPal's public browser identifier and belongs in the page; the matching `paypal-secret` never goes in this repo, and the suite pins both that the shipped value is 80 URL-safe characters and that an empty one renders nothing. Not the `paypalobjects.com/api/checkout.js` the ClickFunnels pages still load: that is PayPal Checkout v4, deprecated, and its flow needs a server endpoint we do not have (Decisions, 2026-10-17).
- P4: `createSubscription` returns `actions.subscription.create({ plan_id })` for this plan, and nothing else. The ClickFunnels page instead posts the whole order form to a ClickFunnels endpoint which then calls PayPal with ClickFunnels' credentials; the modern SDK does that step in the browser against our client id, so the endpoint disappears.
- P5: `onApprove(data, actions)` takes `data.subscriptionID` — the subscription is already live in PayPal at that moment — locks the card form (P10), resolves the buyer's address from PayPal (P6), then fires GA4 `add_payment_info` and `LeskoCheckout.finish({ ok: true }, subscriptionID, address)` — the card path's own success function, with PayPal's subscription id where a Recurly token id would go (K7). The buyer lands on `/welcome?email=…&plan=…` by the one route this page has. There is no `POST /api/subscribe`, no Recurly purchase, no 3-D Secure branch and no decline to retry: PayPal either approved or it did not.
- P6: **the click is never refused, and the buyer's address comes from PayPal** (rewritten 2026-10-23; until then a typed email was required and `onClick` returned `actions.reject()`). Why that was removed: the typed box reaches nothing but `/welcome` and `localStorage`. lesko-provisioning grants Mighty Networks access off `resource.subscriber.email_address` in PayPal's own webhook (`lesko-provisioning/webhooks/rails.py`) and never sees this page, so the refusal protected a display value — and a wrong one whenever the two addresses differ, which is the common case for a PayPal buyer. Measured before removing it: of the only 5 PayPal clicks the live page had ever had, **2 were refused for a missing email**, and neither visitor came back to buy. So `onClick` now only counts the click (P9) and `createSubscription` no longer gates.
  What replaces it, in `onApprove`: `actions.subscription.get()` → `subscriber.email_address`, lower-cased; else the typed box; else `''`, which `/welcome` already renders as a placeholder. PayPal's address wins because it is the one access is granted to.
  That lookup runs **after the money is taken**, so it may never cost the order: it neither rejects nor throws, and an SDK with no `get`, a rejected call, a thrown call, a subscription with no subscriber, and a call that never answers all resolve `''` and finish normally. It gives up after `EMAIL_LOOKUP_MS`, which is bounded by its own check at ≤ 5 s — a bound on how long a buyer stares at a **disabled** button, nothing more, since P10 locks the form first. It was briefly ≤ 1.5 s on 2026-10-23, when the lookup ran with the card button still live and its length was therefore a double-charge window; P10 closed that and the bound was relaxed the same day.
- P7: every failure is shown in `#payMsg`; **never `window.alert`**, which the ClickFunnels page does use — an alert blocks the page and tells us nothing. Carried over from that page's own hard-won comment (its ENG-4226): a failure *after* PayPal approval must not silently lose the order, so `onApprove` failing says "we could not confirm your PayPal payment — if you were charged, contact support before trying again", and `onError`/`onCancel` keep the card form usable. A plain cancel shows nothing.
- P8: the buttons declare PayPal's own funding rule from the ClickFunnels page — PayPal and PayPal Credit allowed, **card funding disabled** (`disable-funding=card`), because our own card field is directly above the button and a second card form there would only confuse.
- P9: the PayPal button reports the funnel of C7, and since 2026-10-23 it sends three of the four names, never `wallet_click_refused` — there is no refusal left to report (P6). `onClick` sends `wallet_click` and does nothing else, so that event is the whole denominator. `onCancel` sends `wallet_cancel` and still shows the buyer nothing (P7). `onError` sends `wallet_error` for a real PayPal failure; no error text and no email are sent. `onApprove` sends exactly one `add_payment_info` (P5), and a `track()` that throws there is swallowed rather than failing the order — PayPal routes a rejected `onApprove` promise to `onError`, so an unswallowed analytics failure would tell a buyer who had already paid that PayPal did not go through.

*Examples:* `?plan=monthly`, switch on → one PayPal button; approval → `/welcome?email=a%40b.co&plan=monthly` and a PayPal subscription on `P-7R176589BE0160805NLJVCFI`. `?plan=half-year` → a button on `P-2GV64945HR320740CNLIP2HY`. A plan name the map has no entry for, or an empty client id → `#wallets` stays empty and no PayPal script is fetched.

*Inputs:* the switch, `?plan=`, the typed email, `LeskoCheckout`. *Outputs:* one PayPal button; one PayPal subscription per approval; one GA4 event; one navigation to `/welcome`.

*Errors:* as P7. Nothing is alerted from the browser, and no server-side decline alert exists for this route because our Worker never sees the payment — which is a gap worth naming: a PayPal failure is invisible to `BTB_ALERT` until the lesko-provisioning side notices.
